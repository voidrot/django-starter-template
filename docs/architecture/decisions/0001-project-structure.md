# 1. Project Structure

## Status

Accepted

## Context

Standard Django project layouts (generated by `django-admin startproject`) often nest the configuration inside a folder with the same name as the project (e.g., `myproject/myproject/settings.py`). This can be confusing and makes it harder to distinguish between project configuration and actual applications. Additionally, app directories are often mixed with configuration files in the root, leading to clutter as the project grows.

## Decision

We have adopted a structured layout that separates configuration from applications:

1.  **`config/`**: Contains all project-wide settings, URL routing (`urls.py`), and the WSGI interface.
2.  **`apps/`**: A dedicated directory for all Django applications (features). All local apps must be placed here.
3.  **Root-level Files**: Only essential tool configuration files (`pyproject.toml`, `mise.toml`, `Dockerfile`) and the `manage.py` script remain in the project root.

## Consequences

**Easier**:
- Navigation is clearer; it's obvious where settings live vs. where feature code lives.
- The project root remains clean.
- CI/CD pipelines and Dockerfiles have a predictable structure to target.

**More Difficult**:
- Developers must remember to namespace imports (e.g., `apps.users` instead of just `users`) unless the `apps` directory is added to the python path (which we do in `config/settings/base.py`).
